> **対象読者:** 初見の開発者、学習・データ処理・描画・評価・GUI担当
> **目的:** 「ユーザーが用意するのは画像だけ」「AIが実際に描いて試行錯誤して学ぶ」を、学習/推論の入出力・失敗条件・再現試験にする。
> **状態:** 新しい学習方式の**規範的設計案**。この文書を書いた時点では学習器・抽出器・高精度Rendererの実装も精度も未検証。

# 画像だけから、実際に描いて学ぶ（Image-only self-practice）

## 0. 最初に知ってほしいこと

> 学習に必要な外部入力は画像のみとする。
> ユーザーおよび開発者は、画像以外の補助データを用意する必要はない。
> タグ・説明文・プロンプトは、必要に応じてシステム側で自動抽出する。

**描く工程の順序は[固定制作工程v2](fixed_drawing_workflow_v2.md)のラフ→下書き→本描き→基本色→陰影・仕上げ→修正・確認→完成に固定**する。人間の筆跡の模倣は不要であり、工程内でどう描くかをAIが試行から学ぶ。タグ・文章の抽出器は利用者が切り替えられる。

AIは正解画像を見ながら「作者の過去の筆跡」を復元するのではない。**自分自身が白紙へブラシで描き、結果と目標画像を比較して、次回の描き方を改善する。** 学習が進むほど、文章だけから自分で描けることを目指す。

**txt2imgの推論時は画像を要求しない**。学習時の目標画像は評価器にのみ渡す。描画Policyが目標画像の画素や特徴を読めたら、学習の核心が成立しない。

| 場面 | 外部に要求する入力 | 処理 |
| --- | --- | --- |
| 学習用データ登録 | **画像ファイルだけ** | 画像を検証 → タグと文章を自動抽出 → 登録 |
| 学習実行 | 登録済み画像データセット | 抽出文章と白紙でAIが描く → 画像比較 → Policy更新 |
| 生成（txt2img） | **文章だけ** | 学習済みPolicyが白紙から自律描画 → 最終画像と履歴 |
| 任意の将来機能 | 手描き実演 | 追加実験に利用可能。ただし基幹学習の必須条件ではない |

## 1. 初見向けの一回の学習例

例として、学習用に「赤いリンゴのイラスト画像」を1枚登録した場合。

1. **画像登録**：画像を読み込み、ファイルハッシュと画像サイズ・色空間を記録する。
2. **自動説明**：設定済みの抽出器が「赤いリンゴ、白い背景」などの文章と `apple, red, fruit` などのタグを出す。抽出文が画像内容と一致しているかは別途評価する。
3. **白紙開始**：描画Policyは文章と白紙、固定256色・ブラシの選択肢を受け取る。**正解リンゴ画像は渡さない**。
4. **まず描く**：固定StageControllerのもとで**ラフ→下書き→本描き→基本色→陰影・仕上げ→修正・確認→完成**の順に進め、Policyが各工程のレイヤー作成、ブラシ選択、色選択、座標列、筆圧、修正を実際に選び、DrawingEngineが一つずつ描画する。必須のラフ・下書き・本描きは飛ばせない。
5. **採点**：評価器だけが「試し描きの画像」と「元のリンゴ画像」を比較し、似ている部分・違う部分・行動の無駄を数値化する。
6. **学習更新**：採点を使ってPolicyの**パラメータを本当に更新**する。次の試行で描画が改善するか同条件で測る。
7. **繰り返す**：同じ画像だけで暗記しないよう、多数の画像・未見画像で改善を確認する。

これが「**描いてみることで学習**」の意味。完成画像から人間の筆跡を逆算することや、固定スクリプトを再生することとは異なる。

## 2. txt2img学習のテキスト条件を画像から自動生成する

**精度向上の正本**：[CaptionとTagの独立抽出・任意N段フォールバック・タグ分類と整形](prompt_extraction_v1.md)。文章とタグは別々のモデルを必ず実行する。Captionは精度の高い登録モデルを優先し、拒否・空文・形式不正などでは**ユーザーが決めた次のモデルを任意段数だけ試す**。Qwenは代替候補の一例であり必須ではない。文章は短文/標準文/詳細文を生成し、人間の通常プロンプトと**同じTextEncoder**に通す。

**外部入力は画像のみでも、モデル内部には文章条件が必要**。CaptionExtractorは画像から説明文を生成し、TagExtractorは同じ画像から独立にタグを抽出・分類・整形する。PromptBuilderは両者を別の成果物として扱い、学習用の自然言語プロンプトを確定する。TextEncoderはそのプロンプトを特徴に変換し、DrawingPolicyが色・形・数・配置・工程内Actionを決めるときに参照する。タグ抽出も必須の前処理とし、**テキスト条件が空のままtxt2img学習を成功扱いしない**。

文章条件を生成できない場合、内部で別の登録済み抽出器やタグからの文章化を試してよい。それでも失敗したら画像IDと理由を保存し、その回の学習対象から除外する。利用者にTXT・プロンプト・タグ・キャプションの入力を要求しない。

**確認するべきこと**：同じ白紙・モデル・seedでも、文章の「赤いリンゴ」と「青いリンゴ」や「一つ」と「二つ」を変えた場合、色・個数・位置などを描き分けられるか未見の文章で測る。画像への類似度だけでなく、文章の意味への忠実度を独立に評価する。

## 3. 自動タグ・プロンプト抽出器は交換可能

画像から出す情報は次の二つ。

- `tags`：対象・画風・色・背景・構図等を表すラベル群。不要なタグ・不確かなタグはconfidenceとともに扱う。
- `prompt`：学習時に描画AIへ渡す自然言語の説明。「赤いリンゴが白い背景に1個」等。存在しない特徴を勝手に足した場合は不確かな抽出結果として記録する。

**抽出器の選択は利用者の設定**。タグ抽出と文章抽出を**別々に必ず実行**する。同じモデルが両方の能力を持つ場合も内部では異なる処理・結果として保持する。CLIと設定JSON・Python登録レジストリでモデルを自由に登録できる。GUIの設定画面は未実装。モデル名はハードコードしない。

```text
登録された画像
  ├─ TagExtractor（ユーザー選択）
  │    └─ tags: [ ... ]
  └─ CaptionExtractor（ユーザー選択）
       └─ prompt: "..."
  → PromptBuilder（バージョン固定）
  → 学習用prompt（システム内部で生成）
  → TextEncoder → DrawingPolicy（文章条件付きで描画）
```

共通API（`image_drawer/dataset/`に[実装済み](image_dataset.md)。モデルを使う抽出器は未実装）：

```text
TagExtractor.extract(image) -> {tags, confidence, language, model_id, model_hash, config_hash}
CaptionExtractor.extract(image) -> {caption, language, model_id, model_hash, config_hash}
PromptBuilder.build(caption,tags,version) -> training_prompt
TextEncoder.encode(training_prompt) -> text_condition
```

- 抽出器レジストリは`id`、`version`、`capabilities`（tag/caption）、`model_hash`、対応言語、実行環境を管理する。これらは**システムの実行設定**であり、利用者が学習画像と一緒に提出するメタデータではない。
- 利用者は**独立したCaption/Taggerのモデル列を任意の順番と段数で登録**できる。タグは一般・キャラクター・作品・rating・画風などに分類し、信頼度や重複を正規化・整形する。**どのモデルに切り替わったか、検証結果、選択した分類・整形設定**を内部で記録し、同じ画像でも異なる実験条件として管理する。
- Cache keyには画像SHA、**CaptionとTagの全登録モデルの順序・ID・設定のハッシュ**、Verifier、Prompt profile/指示、TagNormalizer/Formatterの各バージョンを含める。モデルの追加・順序・分類ルールを変えたら旧結果を無条件に再利用しない。
- 抽出不可／空文字／破綻した文になった場合は品質警告・除外理由を記録し、**ユーザーにプロンプトを必須入力させない**。学習用画像を勝手に捨てた件数も出す。
- 学習画面では抽出結果を閲覧できるが、**手入力・編集を求めない**。画像だけでデータ登録とテキスト条件生成が完結することが通常の受け入れ条件。
- 出力文章の日本語・英語は実装選択可能。**短文・標準文・詳細文の混合**と、生成時の日本語・英語・タグ形式の指示への忠実度を別々に評価する。実際の画像にない属性や無根拠なネガティブ指定を足さない。

登録レジストリ・CLI・HTTPアダプタの基盤は実装対象になったが、実モデルのセットアップ・大量Datasetへの接続・End-to-End精度は未検証。モデル名や「ほぼ無制限」という性質を根拠なく固定しない。

## 4. 学習データは「目標画像」であり「正解の筆跡」ではない

学習の登録素材は**画像だけ**。内部では`TrainingImage{image, image_hash, generated_tags, generated_prompt, extractor_versions, group_id}`のように記録する。ハッシュやIDや抽出結果はシステムが生成し、別ファイルをユーザーに要求しない。

**正解とするのは目標画像と説明の内容**。正解の「次のブラシ」「次の線」「筆圧」は入力に存在しない。画像から教師用の架空の操作列を作らない。

- `target_image`を参照できるのは**学習時のEvaluator/Reward計算**のみ。
- `DrawingPolicy(prompt, current_canvas, layers, history, remaining_budget)`は**目標画像を絶対に受け取らない**。Targetへのencoderや埋め込みをPolicyの入力に隠しても不合格。
- Policyが描いた各Actionは `actor=model` として正直に記録し、成功・失敗候補を含むtrialを `TrainingRollout` として残す。元画像を人間の制作履歴だと称さない。
- 学習中の「描いた画像」は**モデル自身の行動**で生成する。Part配置・img2img変換・正解画像のコピーで報酬を稼いではいけない。
- 外部から受け取る学習素材は画像のみとする。内部の抽出結果やrunログはシステムが作るものであり、利用者や開発者に用意させない。

## 5. 具体的な「描いて試す」学習ループ

これは単なる生成後ランキングではなく、**モデルのパラメータを改善する学習**である。

```text
for 目標画像 in train_dataset:
    prompt, tags = frozen_extractor_results(目標画像)
    text_condition = text_encoder.encode(prompt)  # 空文字ならこのtrialを開始しない
    for trial_seed in training_seeds:
        state = blank_canvas()  # 外部画像で初期化しない
        stages = fixed_stage_controller("illustration-standard-v2")
        actions = []
        while not finish and budget_left:
            action = trainable_policy.sample(text_condition, state, history, stages.current)
            stages.validate(action)  # ラフ→下書き→本描き等の順序と必須strokeを強制
            state = drawing_engine.apply(action, state)
            actions.append(action)
            reward = evaluator.compare(target_image, state.render(), action_cost)
            # target_image を見てよいのは evaluator だけ
        loss = optimize_policy(actions, reward, policy_parameters)
        update_parameters(loss)
        store_rollout_and_metrics()
```

**更新方法のベースライン**：候補Actionを複数試す → 目標との距離の改善により報酬を算出 → **Policy-gradient/actor-critic等の確率的方策最適化**でActionの選択確率を更新する。候補軌跡を再利用する場合も、`actor=model` の自己生成データであることと、更新前Policyのバージョンを保持する。

将来、微分可能なブラシ描画器を導入して画像損失から**モデルの出力に勾配を伝播**してもよい。ただしそれも「実際に描いて結果を評価する」手法であり、**人間の過去の筆跡を推定したことにはしない**。

重要な限界：広いAction空間を**画像の最終一致だけ**で学ぶのは非常に難しい。大量の試行が必要になり、報酬の設計次第では「白背景のまま終了」等の失敗解へ偏る。そのため、下記の段階学習と途中報酬を必須にする。

**重要な情報隔離**：学習中の1回の試行（rollout）において、対象画像から計算したスコアや差分画像を**次Actionを選ぶPolicyの入力に戻さない**。描画Policyが見るのは現在の自分の絵・ステージ・過去のAction・文章だけ。比較スコアは試行後にTrainerが受け取り、次回のPolicyパラメータ更新に使う。正解画像があるから学習できることと、正解画像を見て描くことは異なる。

段階ごとの代理指標と初期の重み・終了報酬は[工程別Rewardの仕様](stage_reward_v2.md)を参照する。高画質が得られることは未検証であり、画像から正解ラフや人間の筆跡を作る方式ではない。

## 6. 報酬と失敗を明確にする

最初の実装は、評価対象を**画素・低周波形状・輪郭・知覚的特徴・文章への忠実度・行動効率**へ分ける。重みは実験設定として固定し、理由なくまとめて1つの「良い感じスコア」にしない。

| 成分 | 目的 | 注意 |
| --- | --- | --- |
| 低解像度/多段階の画像距離 | 位置・構図・全体色を合わせる | 初めから細部の差ばかり見ない |
| 輪郭・領域の距離 | 線画や形状の改善を測る | 目標画像から**評価専用**の特徴を計算してよい |
| 知覚特徴の距離 | 単純な画素一致に依存しない | 特徴量のモデル・バージョンを保存する |
| テキスト適合 | 抽出した説明と描画結果が対応するか | 抽出器の誤説明に引きずられないかを別途確認 |
| 途中進捗 `D(before,target)-D(after,target)` | 一筆ずつの改善を可視化 | 無意味な細かい一筆を大量に繰り返す対策が必要 |
| Action/時間/不正操作コスト | 無限に描き続ける抜け道を防ぐ | 早期finishだけが最適にならないよう最終達成も評価 |
| **工程別の進捗と順序** | ラフの大きな形→下書きの構造→本描き→色→陰影→仕上げ | ステージ順序は固定。学習で自由に選ぶのは各工程内の描き方 |

**最終画質と行動効率の両方**で更新を評価する。`finish`には最終画像品質の評価を必須とし、「すぐ終了して罰則を回避」できない設計にする。画像が完全に一致することは、固定256色やRendererの表現上の限界により必須としない。

報酬を「人間の正解Action」による直接分類と混同しない。**何をしたら作品に近づいたか**を試行から学ぶ。

## 7. 最初からイラスト全般を一気に学ばせない

最終対象は**イラスト全般**だが、最初のベースラインは難度別に段階を踏む。

1. **線・点・単純な形**：色・筆先・座標の合法性、白紙からの描画と更新が成立するか。
2. **単一物体の単純なイラスト**：線・面・色の使い分け。自分で修正できるか。
3. **複数色・複数レイヤー**：下書き・本描き・影などの独立行動。
4. **人物・風景・異なる画風**：言語の指示と画質、一般化、長い制作手順の改善。

技術的な成功条件は**「有効Actionを発行できた」だけではない**。同じ条件の学習前Policyより、未見画像・未見プロンプトで定量・定性評価が改善している必要がある。

## 8. 訓練・評価・再現性の契約

- 画像を受け取った時点で`image_hash`と近重複グループを作り、**作品・作者が分かれば作者も含めてsplitを固定**。タグ/文章抽出器の出力でsplitを操作しない。
- train/test画像を同一のプロンプトや類似画像を介して実質混入させない。抽出器・報酬のモデルがtest画像を暗記できる設定ならその影響を開示。**testの目標画像や抽出文章を使ってModelや抽出器をチューニングしない**。
- 抽出器ID/hashと出力・fallback理由、`prompt_builder_version`、パレット/ブラシ/Control表/Renderer/Rewardのversion・SHA、seed、ハードウェア依存性をmanifestへ保存する。
- 各trialに`target_image_id`（**Policy入力ではない**）、`prompt`、`policy_before`、行動列、各stepのReward成分、完成画像URI、終了理由、`policy_after`を保存する。モデルはどのActionが採択されたか確認できる。
- 学習途中の失敗・無効Action・予算上限は**Datasetから勝手に除外しない**。失敗分母を保存し、成果を選別した画像だけで報告しない。
- 未見画像・未見promptの改善、複数seed、95%信頼区間、失敗例を評価する。**収束・高精度は保証しない**。

## 9. 必須の自動受け入れ試験

1. **画像だけでデータ登録**：ユーザーが画像1枚を選んだ後、txt・タグ・caption・prompt・権利情報・制作履歴・追加メタデータの入力欄を要求せず、システムが必要な抽出を実行する。
2. **抽出器の切替**：Tagger A/B、Captioner A/Bを別々に変えられ、設定変更後はcache・manifest・実験IDが切り替わる。抽出器がない場合は理由を示して停止し、ユーザーに追加の入力素材を要求しない。
3. **テキスト条件の学習**：自動抽出した非空プロンプトがTextEncoderに入り、対応する言葉（対象・個数・色・位置）の変化によって描画が適切に変わるかを独立に評価する。空文は学習成功に数えず、ユーザーによる補助ファイルの入力を要求しない。
5. **固定制作工程**：全7工程を順に通過し、`skip_stage`や逆戻りは一律拒否。ラフ/下書き/本描きは独立した有効な筆跡が必要。基本色/陰影/修正は**工程内の理由付きレビュー**を許す。各工程でどのブラシ・色・位置を描くかはPolicyが学習する。
4. **Policyの情報隔離**：Policyへ渡す観測に`target_image`・target特徴・正解Actionを混入させない。Evaluatorだけがtarget画像を取得する。目標画像を別画像にすり替えても、**同一prompt/seed/checkpointの最初のPolicy Actionは変わらず**、Rewardのみ変わる（Policyに勾配を適用する前）。
6. **本当に描いたか**：空白からレイヤー・色・ブラシ・ストローク・修正をActionとして呼び出す。完成画像が正解画像へのコピーや一括img2img生成ではない。ActionからReplayで再現できる。
7. **本当に学んだか**：報酬に基づく更新で重みまたは訓練可能なPolicyパラメータが変わる。更新前後の確率/損失を比較する。選択された筆跡を固定スクリプトとして保存しただけでは不合格。
8. **最小の収束試験**：**少数の単純画像だけ**から学習し、固定seedで多数trial後、停止条件と比較対象を固定して、モデルの未学習baselineより画質・報酬が改善することを確認する。Toy画像に対応するAction列は学習器へ絶対に渡さない。
9. **一般化の検証**：trainと異なる画像/色/単語で評価し、出力が同じ画像の暗記やprompt無視になっていないかを測る。
10. **推論は文章のみ**：学習済みモデルが外部画像なしで白紙から自分で描き、PNG/画像とAction履歴を返す。target画像を必要とする学習Evaluatorは推論で起動しない。

本項のテストは**将来実装する必須要件**。CIで仕様文書・JSONだけが通っても、自己描画学習が完成したと主張しない。
