> **対象読者：** Image Drawerの学習器・評価器・固定工程の実装担当
> **目的：** 画像だけを教材として、各工程で「何を改善したら学習できたといえるか」を検証可能にする。
> **状態：** **数値は初期ベースラインの設計値**。実画像による精度比較・レンダラv2・特徴量の画素Goldenはまだ未実装。

# 画像だけで学ぶための工程別評価（Reward）

## 1. 評価器は「見本画像」を見てよいが、描くAIは見てはいけない

例えば利用者が赤いリンゴの完成画像だけを登録したとき、ソフトが自動で説明文を作る。描画AIには**「赤いリンゴ」という文章と、自分の描いたキャンバス・現在の工程**だけを見せる。

**採点する別の部品（Evaluator）だけ**が元画像と現在の絵を比較する。描画AIの観測には、元画像の画素や埋め込み、元画像から生成した「正解のラフ」、**同じ試行中の目標画像依存Reward**を入れない。

もし描画AIが一筆ごとに「右に描けば正解画像に近づく」と教える**目標依存の評価結果**を直接読めたら、生成時に存在しない画像を間接的に見たことになる。**トライアルが終わってから、Trainerだけが採点結果を使ってモデルを更新**することが今回の初期学習契約。学習方法の比較は将来の独立版で扱う。

## 2. 工程ごとに見るものを変える

完成画像しか存在しないため、実際の絵師が描いた中間ラフや下書きを正解として用意しない。代わりに、**目標画像から自動計算する画像の特徴**を使い、各段階での改善を測る。

| 工程 | 主に比較する特徴 | それで分かること・限界 |
| --- | --- | --- |
| ラフ | 小さな画像の大まかな輪郭 | 形・位置の大まかな一致。ラフの正解筆跡は分からない |
| 下書き | 小〜中解像度の輪郭 | 比率や位置の改善。輪郭だけで内容が正しいとは限らない |
| 本描き | 中〜高解像度の輪郭 | 線と形の確定。厚塗りの評価には補助指標が必要 |
| 基本色 | 低解像度RGB・色の分布 | 主な色・広い面の一致。細部は別工程 |
| 陰影・仕上げ | 明暗と色の全体配置 | 明暗や立体感の改善。質感そのものは別評価が必要 |
| 修正・確認 | 細かい色・輪郭・全体色 | 変更による最終的な改善 |

**これらは仮の代理指標**であり、正解画像が唯一の「正解の工程」であるとみなすものではない。

## 3. 初期評価スコアの決め方

[機械可読な初期重み表](stage_reward_v2.json)を正本とする。各特徴スコアは**0〜1（大きいほど良い）**に正規化してから重み付き合計する。

| 工程 | 初期の重み |
| --- | --- |
| ラフ | 32px相当の粗い輪郭：**100%** |
| 下書き | 粗い輪郭：30%、中程度の輪郭：70% |
| 本描き | 中程度の輪郭：40%、細かい輪郭：60% |
| 基本色 | 低解像度RGB：70%、色分布：30% |
| 陰影・仕上げ | 明るさの分布：65%、低解像度RGB：35% |
| 修正・確認 | 高解像度RGB：55%、細かい輪郭：25%、低解像度RGB：20% |

たとえば下書きのスコアは、

```text
score_sketch = 0.30 * edge_32 + 0.70 * edge_64
```

の形で計算する。ここで`edge_32`等は元画像と今の描画の比較結果であり、**モデルへ入力される画像ではない**。

**数値をfreezeする前の未解決事項**：画像縮小アルゴリズム、Sobelの輪郭検出、しきい値、RGBの色空間、アルファの背景合成、スコアの正規化。これらの入力と期待値を持つ**別のGoldenテスト**をv2 Renderer/Reward実装Issueで必ず作る。現在の表が実装済みだと主張しない。

## 4. 一筆ごとにどう報酬を得るか

最初のベースラインは**描く前後でその工程のスコアがどれだけ改善したか**を使う。

```text
step_reward =
  stage_score_after - stage_score_before
  - 0.05 / max_actions
```

これによって「一筆引いたら少し形が近づいた」なら正の報酬、「形が崩れた」なら負の報酬になる。すべての操作に少しだけ行動コストを付け、無限に細かい線を引き続けることを防ぐ。**工程を変えるだけで画像が改善していないのに大きな報酬を与えない**。

最後の合法な`finish`では、完成画像の品質スコアの**2倍**を追加報酬として候補にする。予算切れ・不正終了には失敗のペナルティ。モデルが「ラフだけ描いてすぐ終了する」ことを最適解にしない。

- `max_actions`はWorkflowで定義された予算。パラメータ更新に使う場合は、採点結果とそのActionの選択確率（または微分可能な描画計算）をTrainerが利用する。
- 無効Actionは採点とattempt数を記録するが、画素が変更されたことにしない。
- Stageを切り替える際は、**変更前・変更後で比較する工程スコアを混ぜない**。ステージ境界の報酬は別扱いとし、意図しないスコアのジャンプを利用して得点できないようにする。
- モデルの重みを実際に更新することと、画像の品質が改善することは**別の検証項目**。

初期数値は**実演データの人気設定ではなく、比較実験の開始点**。過度な行動コストや特徴量の偏りは学習を失敗させる可能性があるため、他の候補との比較を行う。

## 5. なぜ「ラフで完成画像と画素一致」を要求しないか

ラフは粗い線だけなので、着色済みの見本画像とピクセル単位で一致させると、**ラフの段階でいきなり全面を塗り始めるように学習してしまう**。

工程別に比較対象を変えれば、ラフでは位置や輪郭を先に学ぶ余地ができる。ただし輪郭だけの報酬で形の意味理解まで保証するわけではない。固定工程だけで画像が上手になる保証もない。

**完成時の品質評価は工程別の指標とは別に行う**。未見画像や未見プロンプトで、対象・数・色・位置関係が指示と合っているかを独立に測る。抽出した文章が誤っていた画像は、抽出器の品質問題として集計する。

## 6. 自動試験で必ず検証すること

1. **同じプロンプト・seed・checkpointのPolicy**は、目標画像だけ差し替えても最初のActionが同じ。Scoreだけが変わる（パラメータ更新前）。
2. 途中スコアをPolicyへ直接渡さない。Trainerが受け取るのはTrialと採点結果、Policyが受け取るのは文章・stage・**自分が描いたStateと履歴**だけ。
3. 各工程の重みは合計1、未知のfeatureは拒否、同じ設定で同じ採点を出す。
4. 何も描いていないのにStageを進める／白紙で`finish`した場合は、固定工程Controllerが拒否するか明確な失敗評価になる。
5. 同じモデルで、Trial前後の重みが変わったか、学習前後に未見画像品質が改善したかを**別々に測る**。
6. 固定256色で表現できない色もあるため、**目標画像の画素完全一致を学習成功条件にしない**。色誤差分布は計測する。
7. Rewardが高くても、固定の線を数本描いただけ・画像をコピーしただけ・禁止レイヤーへの筆跡なら**描画過程の検証で不合格**にする。
