> **対象読者:** 画像登録・自動タグ付け・学習Dataset・評価・再現性を実装する開発者
> **目的:** 利用者が用意するのは**画像ファイルだけ**であることを保証し、説明文の自動抽出と学習データの品質を管理する。
> **状態:** 規範的な**画像のみの学習設計案**。抽出器や学習器の実装はまだ存在しない。

# 学習画像・自動タグ／プロンプト抽出の品質仕様

## 1. 何を準備するか

> 学習に必要な外部入力は画像のみとする。
> ユーザーおよび開発者は、画像以外の補助データを用意する必要はない。
> タグ・説明文・プロンプトは、必要に応じてシステム側で自動抽出する。

txt2imgの学習には**内部のテキスト条件**も使用する。ただしこれは外部入力ではない。画像から文章を作り、TextEncoderで変換して描画Policyへ渡す。人間の制作履歴も必要ない。

| 要素 | だれが作るか | 学習での役割 |
| --- | --- | --- |
| 元の画像 | ユーザー／開発者が登録 | **目標画像**。評価器だけが試し描きとの比較に利用 |
| タグ | 選択したTagExtractor | 内容や画風などの自動ラベル。正答保証はない |
| 説明文・prompt | 選択したCaptionExtractorとPromptBuilder | **内部で生成するテキスト条件**。手入力は不要 |
| 文章の特徴 | システム内部のTextEncoder | 描画Policyが文章の内容に応じて描き分けるための特徴 |
| 筆跡・ブラシ操作 | **モデル自身が試し描きする** | 記録した結果と報酬からPolicyを改善 |

この区別の正本は[画像のみで描いて学ぶ仕様](image_only_learning_v1.md)。機械可読な[外部入力・内部生成の契約](training_input_v1.json)も参照する。

## 2. ユーザーが選ぶ自動抽出器

- **タグ抽出器とキャプション抽出器は別の設定**。同じ実装が両方できる場合もアダプタで共通APIに合わせる。利用者はモデルを切り替えるだけで、テキストファイルを別途用意しない。
- GUI・CLI・設定ファイルから選べる。利用者が切り替えると、同じ画像でも**別の抽出結果バージョン**として保存し、古いキャッシュを使わない。
- どの抽出器を使用したかは`tagger_id/model_hash/config_hash`、`captioner_id/model_hash/config_hash`、`prompt_builder_version`をデータごとに記録。
- `tags`はラベル・confidenceを保持。文章は`caption`と`training_prompt`を区別し、PromptBuilderがどのように両者を組み立てたかをversion管理する。
- モデルが画像にない特徴を記述する場合がある。**自動抽出は正解ラベルではない**。空文・低信頼・不適切な文字列は品質エラーとしてマークし、利用者へタグの手入力を強制しない。
- 対応モデルが利用できない場合、データ登録と学習開始のどこで止まったかを明示する。**タグやプロンプトの手入力を要求して回避しない**。文章条件が得られない画像は失敗理由を保持し、その回のテキスト条件付き学習から外す。

抽出器レジストリの実装方法、設定変更・キャッシュの一意性、利用可能なモデルは[画像のみの学習仕様](image_only_learning_v1.md#2-自動タグプロンプト抽出器は交換可能)が正本。

## 3. 画像1件の内部データ例

JSONは構造説明用で、まだ実装済みのschemaではない。

```json
{
  "image_id": "img_sample_001",
  "image_sha256": "<sha256-of-file>",
  "split_group": "work_001",
  "image_uri": "dataset://work_001/image.png",
  "tagger_id": "selected-tagger",
  "captioner_id": "selected-captioner",
  "prompt_builder_version": "prompt-builder-v1",
  "tags": ["apple", "red"],
  "training_prompt": "白い背景に赤いリンゴが1個",
  "extractor_output_version": "extract-v1",
  "split": "train"
}
```

上記の`tagger_id`等は**例示名**であって実装済みのエンジンではない。ID・ハッシュ・画像の分割・抽出結果は**ソフトが内部で生成・管理**する。ユーザーが用意するものは画像ファイルだけ。

## 4. データ登録の必須チェック

1. **ファイルを読む前**にサイズ・種類・サポート形式を検査する。静止画像を対象とし、アニメーションや壊れたファイルを暗黙の1フレーム変換で紛れ込ませない。
2. EXIF回転、sRGBの変換、リサイズ・クロップ、alpha背景の扱いを**version付き処理**で統一する。解像度変更は教師画像を黙って上書きしない。
3. **完全一致ハッシュ＋近重複検出**で同一作品をgroupにまとめる。派生画像・クロップ・色調変更のtrain/test跨ぎを避ける。
4. **画像をsplitしてから抽出器やPolicyの検証に使う**。trainから抽出器設定を調整し、固定testを何度も学習調整に使わない。
5. 抽出器の出力を保存し、空のprompt・不正なタグ・説明の矛盾・低信頼・失敗件数を一覧にする。失敗した画像を無断で除外しない。
6. **対象画像を描画Policyの観測へ混ぜない**。読み取れるのはTrainerのEvaluatorだけ。Dataset loaderは`policy_input`と`reward_target`を別データ型で返す。
7. 学習成果を報告するとき、画像件数・画風・解像度・train/validation/test split・抽出器別の分布と欠損・重複率を示す。

## 5. 自動描画の履歴は元画像から作らない

**モデルが実際に描いた試行**だけを`actor=model`で記録する。そこには選択ブラシ（12種）、固定256色、サイズ19段階、不透明度11段階、筆圧11段階・パターン、レイヤー、軌跡、終了や失敗理由を含める。

- 元画像から「作者の正解Action列」を推定しない。画像が似ていても**作者が使った本当のブラシ・筆圧・レイヤーは分からない**。
- 採点に使った目標画像ID、抽出prompt、抽出器version、Renderer、Policy before/after、Reward component、seedと各試行の成功・失敗を保存する。
- **画像の報酬を使ってPolicyの学習パラメータが更新されたか**を追跡する。固定ActionScriptの繰返しは学習ではない。
- 説明を付けるAIと、描くAIを混同しない。抽出器が勝手に絵を描いて返す方式は禁止。

## 6. データが十分かの判断

利用者が何枚か登録できたというだけで、イラスト全般の学習が成立するわけではない。**単純図形→単一対象→多色・多レイヤー→イラスト全般**の段階で、対象画像だけから試行・報酬・Policy更新が機能することを測る。

必須報告：登録画像数、有効画像数、画像重複、タグ/プロンプト抽出成功率、生成Action数、無効率、Reward改善、学習前後の画質、計算資源と学習時間。**高精度を約束したり、ユーザーの画像が少なくても必ず学べると断言しない**。

## 7. バージョンと互換性

`image_dataset_hash`、画像ごとの`sha256`、画像正規化version、TagExtractor/CaptionExtractor/PromptBuilderの全versionとhash、抽出結果、固定256色palette、brush set、control levels、renderer、reward、Policy checkpoint、学習seedを一緒に保存する。

変更で抽出結果やAction意味が変わる場合、**キャッシュを無効化し新Dataset/Checkpoint実験として区別**。既存のDrawingEpisode v1のスキーマ・goldenは変更しない。

この仕様を導入しても、現時点の**抽出器実装・画像学習・高画質生成の完成を意味しない**。
