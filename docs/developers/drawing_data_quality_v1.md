> **対象読者:** 人間の描画の収集・前処理・Dataset・Replayを実装する担当者
> **目的:** 行動学習で使用する教師データの真正性・再現性・品質を固定する。形式は[制作過程v1](drawing_process_v1.md)を参照。
> **状態:** 設計レビュー用の規範的仕様案。収集した実データはまだない。

# 人間の制作行動：収集・復旧・データ品質仕様 v1

## 1. 学習精度を決める最重要データ

完成画像からは「いつ・どこを・どのレイヤーに・何色の筆で・何回描いたか」を一意に復元できない。**人間の実操作を収集することが必須**。同じ画像を作る多数の行動列があり、最終画像だけで教師ラベルを作ると推定と実演が混在する。

`origin=human`のラベルは**人間が本当に行ったActionEvent**のみに用いる。`actor=human`は各イベントの出所であり、`origin=mixed`の中にも存在し得る。`actor=model`・`system`・`synthetic`・`derived`を人間の正解として誤投入しない。

収集方法の第一優先：実際にブラシ・色・レイヤーを操作できる専用GUI。録画動画や完成PNGは補助的な観察材料であって、原始操作の代替ではない。

## 2. 収集する情報と欠損の区別

| 内容 | 必須／保存方法 | 注意 |
| --- | --- | --- |
| Promptと作品・セッションID | `episode_id`、`prompt`、`artwork_group_id` | 同一作品のバージョンは同一group |
| 操作者 | 匿名化した`artist_group_id`、各イベントの`actor` | PIIは研究datasetへ入れない |
| 操作の順番と時間 | `seq`、`time_ms`、実操作の因果順 | UI表示時計ではなくmonotonic clockから相対時間を生成 |
| 操作と道具 | `select_color`、`select_brush`、`select_layer`、`stroke`、`erase`等 | 暗黙の変更を学習データへ紛れ込ませない |
| 画像の変化 | `DrawingEngine`で中間状態を再生。選択色・レイヤー・全筆跡を保持 | 完成PNGだけでは不合格 |
| 画面入力 | 生ポインタ（未量子化の座標・時刻・端末種別・入力順）を**別のrestricted sidecar**へ保存可能 | 生イベントからActionへの丸め・重複除去はversion付け。v1のActionは整数座標 |
| 出所と学習権限 | `consent_scope`、`license`、`source_uri`、`collection_version` | `origin=human`という文字列は学習許諾を証明しない |

`phase`の人間ラベルが欲しい場合、GUIで描画前に**本人に明示選択させる**。アプリが勝手に挿入したものは`actor=system`。推定したphaseを`actor=human`と偽らない。下書き、色塗り、影、修正などは本人がどの順で実行してもよい。評価時は本人の解釈と一致していることを確認する。

`DrawingAction`では色のRGBA数値ではなく**固定の`color_id`**を保存する。`brush_id`は完全に独立。複数レイヤーを平坦化して表示画像だけを残すことは禁止。

## 3. 正規化の境界（raw・action・trainingを混同しない）

```text
raw pointer/tool events（不変、収集順）
  -> versioned input normalizer（表示座標→画素、切断、重複処理）
  -> DrawingEpisode events（意味論の正本）
  -> validated Replay（中間レイヤーの完全再現）
  -> training examples（状態のprefix -> 次のAction）
```

raw→Action正規化には`normalizer_version`、画面倍率、キャンバス寸法、点の間引き手順、入力中断理由を記録。学習時に幾何形状を勝手に滑らかに補間して、それを人間の実演と主張しない。描画器v1の整数丸めによる形状損失は測定して公開する。生の高分解能操作を将来のサブピクセル描画器へ移すときは別versionで再生成し、v1履歴を上書きしない。

**重要：** 公開されたQuick, Draw!などのストロークデータは初期研究には有用でも、色・ブラシ・複数レイヤー・修正の教師ラベルを含まない場合は**それらの学習対象の正解データとして使わない**。存在しない操作を捏造しない。

## 4. パレットの品質管理：固定256色を守って最適化する

**「256色固定」は確定方針、個々のRGB値は別の設計承認事項。** 旧案の`216色RGB立方体＋40グレー`が本当に最適とは仮定しない。

- 色候補の設計時に、**利用許諾を得たtraining側だけ**から、人間が選んだsRGB色の頻度と用途（線、下地、肌、影、背景など）を集計する。validation/testをパレット選定に使用しない。
- 比較候補：従来の固定256色案／訓練側の色出現を重み付けした256メドイド／階調と重要色域の最低枠を確保した256メドイド。知覚的な比較距離として**OKLab**を使う候補を評価するが、これはRGBを直接予測する方式への回帰ではない。
- 同じ色番号`0..255`の分布・色の知覚誤差・各カテゴリの最大誤差・頻度・視認性を報告。**平均誤差だけで判断せず**、肌色・暗部・高彩度の少数例も評価する。
- 選んだ**256個のRGB8と順番を一度だけfreeze**し、全エピソード・train/val/test・推論で同じ`palette_id`とSHA-256を使用。モデルcheckpointもpalette hashを持ち、違えばロード拒否。
- 一度承認したpaletteは途中で変更せず、新規versionとしてdatasetを完全再生成。完成画像を256色に量子化しない（半透明合成は中間色を生成してよい）。

設計レビュー前のRGB表を「最適なパレット」と称しない。固定256色の範囲内で表現力を検証することが目標。

## 5. データゲート（不合格は学習に流さない）

各エピソードに次の検査結果を付ける。`passed=false`が一つでもあればそのエピソードをtrainingへ入れず、理由を集計する。

1. JSON厳密検証：サイズ・数値字句・同名キー・型・actor・origin・時刻・seq・各Action payload。
2. 意味検証：存在するレイヤー／選択中の色・道具・工程／`finish`／レイヤー制限／リソース予算。
3. 再現性：保存→読み込み→再生した全状態と、収集時に記録した各checkpointの**レイヤーRGBA画素hashが一致**。完成画像だけ一致するのでは不足。
4. 出所・許諾：学習許可の明示、収集方法、グループ単位、権利に問題がないこと。
5. 主体別検証：`origin=mixed`は各`actor`を再確認。人間がモデルの誤りを訂正した行動と、独立して最初から描いた実演を**別ラベル**で保持。
6. 品質観察：空操作、同じ色・道具の連続切替、終了前の中断、量子化で消えた操作、極端なストローク長、クラッシュ回復を**除外理由または統計**として記録。自動修正で人間の行動を改変しない。

入力の正規化でActionが変わる場合は、元rawイベントへの参照を残す。画素一致率100%は**同一描画器の再生保証**であり人間に似た絵を描くモデルの精度保証ではない。

## 6. 中断復旧・Artifactと学習datasetの整合

Journalはイベント1件ごとにappend→flush→fsync→ACKし、`DrawingDraft`で中断状態を復旧する。`finish`未記録のDraftは学習に自動投入しない。再開時に当時のパレット・ブラシ・レイヤー状態をReplayし、時刻とactorを改竄せずに続ける。

完成Episode blobをSHA-256内容アドレスでpublish→同一トランザクションのmanifest/outboxへ`episode_uri/hash/artifact_id/run_id/status=committed`を記録。blobのみ／参照のみの状態を起動時に照合し、破損・欠損・孤立は隔離してレポートする。`committed`かつ全検査合格のものだけDataset builderが読む。永続化方式（SQLite/WALまたはatomic manifest）は1種類を選んで実装Issueに固定し、**再起動クラッシュ試験**を必須とする。

## 7. 分割・重複・権限の管理

- 最低限、`artist_group_id`／`artwork_group_id`／`source_session_id`／`dataset_version`を持つ。同じ作者・同じ作品の派生・共同編集episodeを異なるsplitへ跨がせない。
- **未知作品評価**：work groupで分割。**未知作者評価**：artist groupで分割。両方を別々に報告し、良い方だけを選ばない。
- 同じpromptの文字列や画像・完全一致Action hashだけでなく、シリーズ作品の流用を監査する。近重複を発見した場合はgroupを併合し、splitをやり直す。
- validationはハイパーパラメータ調整に使える。testはfreeze後の**一回の最終判定**を基本とし、テスト結果に合わせて設計を繰り返す場合は新しいtest集へ更新したことを記録。
- 消去要求・学習許諾取り消しがあれば対象エピソードと派生datasetの利用停止を追跡できるmanifestを保持する。個人識別情報は私有データ領域で別保管。

## 8. 必須統計・データ収集の合格条件

収集後、次を`artist_group_id`単位・split単位・phase別に一覧化する：

- 有効／不正／途中中断Episode数、実演時間、Action数・stroke数・point数、全レイヤー数。
- `Action`型・`color_id`使用分布、線幅・不透明度・stroke長、空操作・消去／修正率。
- 出所別（human/model/system/derived）の件数、`mixed`の比率、学習対象として使える件数。
- checkpointのlayer hash一致率、raw→Action量子化の軌跡ずれ、パレット誤差の分布。
- artist、作品カテゴリ、サイズ、難度ごとのカバレッジ不足。

**合格**：入力を権利・出所含め検証でき、同じAction列で中間状態が完全一致し、未来漏洩のないDatasetへ変換できる。実データがない場合は「学習データの品質未評価」と報告する。「これだけ集めれば高精度」という保証はしない。

## 参考（非規範）

- [Quick, Draw! raw dataset](https://github.com/googlecreativelab/quickdraw-dataset) は線の時系列データの例。色・レイヤーの教師としては使えない場合がある。
- [OKLab](https://bottosson.github.io/posts/oklab/) はパレット候補の知覚誤差を調べる手段であり、RGB値のパレット確定を自動的に保証しない。
