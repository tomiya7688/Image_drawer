# 共同作業ルールとワークフロー

**対象読者:** このリポジトリで作業するCodex、Claude、ChatGPT、Copilotなどのコーディングエージェント  
**目的:** 複数のエージェントが同じ`main`へ変更を集める際の衝突、滞留、品質低下を防ぐ。

エージェントごとの入口は共通です。コードの書き方は[コーディング規約](coding_conventions.md)に必ず従ってください。このファイルは進め方だけを定め、技術仕様は複製しません。

## 1. 原則

- `main`は常にCIが成功する状態に保ちます。`main`へ直接pushしないでください。
- 作業は作業ブランチとPull Request(PR)を通します。
- エージェント間の連絡はGit履歴、Issue、PRに残します。会話内の了解事項は、PRかIssueへ書き戻してください。
- 未コミットの変更は他のエージェントや利用者の作業かもしれません。破棄、stash、上書きをしないでください。扱えない場合は、作業を止めて利用者へ確認してください。

## 2. 作業開始時の手順

1. 最新の状態を取得してください。毎回必ず実行し、省略しないでください。

   ```bash
   git fetch origin --prune
   git switch main
   git pull --ff-only origin main
   ```

2. **オープン中のPRと、Issueの優先度を確認してください。** 次の1コマンドで、先に処理するPR、優先度順のIssue、優先度が未設定のIssueを一覧できます。

   ```bash
   python scripts/check_triage.py
   ```

   `python scripts/check_local.py`にも同じ確認(`triage`)が含まれます。PRや優先度の未設定がある場合は`WARN`と表示されますが、失敗終了にはなりません。`gh`を使えない環境では理由付きの`SKIP`になります。

3. `git status`で未コミットの変更を確認してください。`main`へ切り替えられない場合は、変更を保ったまま別のクローンで作業するか、利用者へ確認してください。
4. 担当するIssueを確認し、着手をIssueコメントに残してください。同じ範囲を別のエージェントが担当している場合は、重複して実装しないでください。
5. 対象機能の開発者向け仕様と関連テストを読んでから変更してください。

## 3. 作業の順序と優先度

作業は**PR → P0 → P1 → P2 → P3**の順に進めます。オープン中のPRがある間は、新しいIssueに着手しないでください。同じ優先度の中では、依存関係を優先し、依存がなければ番号の小さいIssueから進めてください。

- **起票時に優先度を付けてください。** Issueテンプレートの「優先度」欄でP0〜P3を選びます。テンプレートを使わない場合は、ラベル`priority: P0`〜`priority: P3`、またはタイトル先頭の`[P1]`のいずれかで示してください。
- **優先度が付いていないIssueは、作業側が割り振ってください。** `python scripts/check_triage.py`が示すコマンドで`priority:`ラベルを付けます。判断に迷う場合は、P2を付けて根拠をIssueコメントに残してください。
- P0は、通常の作業より先に着手するセキュリティ対応や、開発を止める不具合に使います。P1は共通の品質・開発基盤、P2は通常の機能開発、P3は後回しにできる改善に使います。

## 3.1 PRの処理を優先する

PRが滞留すると、依存関係の把握が難しくなり、`main`との差分と競合が増えます。新しい実装を始める前に、オープン中のPRをすべて次のいずれかの状態にしてください。

| 状態 | 処理 |
| --- | --- |
| マージ可能 | 差分とCIを確認し、問題がなければマージする |
| 競合または`main`への追従が必要 | 最新の`main`を取り込み、競合を解消し、CIの成功を確認する |
| 修正が必要 | 修正してCIとテストを通し、再レビューしてからマージする |
| 重複・不要・陳腐化 | 差分と他のPRを確認し、理由をコメントしてcloseする |
| 処理できない | 待っている内容と次の行動をPRのコメントへ残す |

- 依存関係とマージ順を見て、土台になるPRから処理してください。PR番号の順では処理しないでください。
- 1件マージするたびに、残りのPRの競合、CI、前提条件を再確認してください。
- 他のエージェントが作成したPRも対象です。差分を確認し、CIが成功して問題がなければ、同じ基準でマージしてください。
- Draft PRも放置せず、継続、修正、closeのいずれかを決めてください。
- 差分を確認せずにcloseしないでください。CIが失敗しているPRをマージしないでください。

## 4. 作業中の規則

- 作業ブランチは`main`から作成し、名前を`<agent>/<Issue番号>-<要約>`の形式にしてください。例: `claude/42-collaboration-workflow`
- 1つのPRには1つの目的だけを含めてください。目安は差分500行以下です。超える場合は分割してください。
- 無関係な整形、リネーム、書き換えを同じPRに混ぜないでください。
- 他のPRと同じファイルを変更する場合は、先にそのPRを処理するか、Issueで調整してください。
- 作業が長引くときは、定期的に`git fetch origin`して`main`の更新を取り込んでください。
- 共有済みブランチへの`git push --force`、`--no-verify`によるフックの回避、テストの削除やスキップによる成功扱いを禁止します。
- 秘密情報、個人の画像、モデルの重み、生成レポートをコミットしないでください。保存場所は`data/README.md`に従ってください。
- コミットメッセージは`type(scope): 概要`の形式(`feat`、`fix`、`docs`、`test`、`refactor`、`ci`、`chore`)にしてください。

## 5. 作業終了時: PRの作成

作業が終わったら、必ずPRを作成してください。ローカルだけの状態で作業を終えないでください。

1. 変更に応じたテストを実行してください。通常は次のコマンドを実行します。

   ```bash
   python scripts/check_local.py
   ```

2. `git fetch origin`して`main`との競合を確認し、競合があれば解消して再テストしてください。
3. ブランチをpushし、PRを作成してください。

   ```bash
   git push -u origin HEAD
   gh pr create --base main
   ```

4. PR本文は[PRテンプレート](../../.github/pull_request_template.md)に従い、対応Issue、変更内容、確認した範囲、確認していない範囲を書いてください。実行していないテストを成功と書かないでください。

## 6. CIの確認、自己レビュー、マージ

1. CIの完了を確認してください。失敗した場合は原因を調べ、同じブランチへ修正を追加してください。CI設定を緩めて通さないでください。

   ```bash
   gh pr checks <PR番号>
   ```

2. `gh pr diff <PR番号>`で差分全体を読み、次の項目を自己レビューしてください。
   - 目的外の変更が混ざっていない。
   - [コーディング規約](coding_conventions.md)(命名、責務、宣言コメント、処理コメント、ファイル長・関数長)に従っている。
   - 正常系、失敗系、境界値のテストがあり、モックの成功と実データの成功を区別している。
   - 依存関係を`pyproject.toml`に宣言している。
   - 秘密情報や生成物が含まれていない。
   - 仕様が変わる場合、`docs/developers/`と`docs/users/`を日本語で更新している。
3. 問題を見つけたら修正し、CIと自己レビューをやり直してください。
4. CIがすべて成功し、自己レビューで問題が残っていない場合に限り、マージしてください。

   ```bash
   gh pr merge <PR番号> --merge --delete-branch
   ```

5. 次の場合は、マージせずPRを開いたまま利用者へ報告してください。
   - CIが失敗し続ける、または原因が自分の変更範囲外にある。
   - 規約の解釈や仕様の判断が必要である。
   - 公開API、データ形式、依存関係を大きく変更する。
   - 他のエージェントのPRやIssueと衝突している。
6. マージ後は`git switch main`して`git pull --ff-only origin main`を実行し、作業ブランチを削除してください。

## 7. 完了報告

作業の最後に、次を利用者へ報告してください。

- PRのURLと、マージしたかどうか。
- CIの結果と、ローカルで実行したテスト。
- 自己レビューで見つけた問題と対応。
- 未実行の確認、既知の制限、後続作業。
