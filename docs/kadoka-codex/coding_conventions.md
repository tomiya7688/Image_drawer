# コーディング規約

この規約は、Image Drawerの新しいコードと、修正・レビューするコードに適用します。既存コードを一括変更する必要はありません。ファイルを変更するときは、その変更範囲で規約に合わせ、無関係な整形や書き換えを混ぜません。

## 1. 読みやすさと命名

- 名前は、値の意味、処理の目的、クラスの担当範囲を具体的に表してください。
- 関数名は動作を表す動詞から始めてください。曖昧な `handle`、`process`、`data`、`item` だけで役割を済ませないでください。
- 真偽値は `is_`、`has_`、`can_` などで条件を表してください。
- 同じ概念には同じ語を使い、同じ名前を別の概念に流用しないでください。
- 略語は一般的なものに限ってください。プロジェクト固有語は最初に定義してください。
- PythonではPEP 8に沿った `snake_case` の関数・変数名と `CapWords` のクラス名を使ってください。
- 型ヒントを付け、公開境界では入力・戻り値の型が分かるようにしてください。

## 2. 責務とまとまり

- 状態と、その状態を一貫して操作する振る舞いには所有者を持たせてください。生成・検証・保存・変換などを束ねる意味のある所有者がある場合はクラスにしてください。
- 単純で状態を持たない処理は、クラスを作らずモジュール関数にしてください。クラス化そのものを目的にしないでください。
- 一つのクラスは一つの変更理由を持つようにしてください。独立した入出力、永続化、判断、表示などを一クラスに集めないでください。
- 一つの関数は、一つの処理単位を実行してください。処理順の調整だけを行う関数は、細部を責務ごとの関数へ委譲してください。
- 外部から変更可能な状態を必要以上に公開しないでください。状態を更新する場所と不変条件を明確にしてください。
- 既存のStep、Backend、Repository、Evaluator、Registryなどの拡張点を使い、中心ロジックに型名・文字列名の分岐を積み重ねないでください。

## 3. 宣言コメント: JSON-like Comment Outs

クラス、関数、メソッドの直前に、責務・処理・状態・入出力が分かるコメントを置いてください。形式の考え方は[JSON-like Comment Outs仕様](https://github.com/tomiya7688/Json-like-comment-outs)に従い、説明する言語とキーは日本語で統一してください。

クラスには「責務」と「フィールド」を書き、主要な振る舞いを「処理」に書いてください。関数・メソッドには「責務」「処理」「引数」「戻り値」を書いてください。副作用、エラー、補足が重要な場合は、それぞれの項目を追加してください。

```python
# {
#   責務: [
#     PartRepository: PartとSourceImageの永続化および検索を担当する
#   ]
#   フィールド: [
#     connection: Part BankのSQLite接続
#   ]
#   処理: [
#     1: PartとSourceImageを同じトランザクションで保存する
#     2: IDと参照整合性を検証する
#   ]
# }
class PartRepository:
    ...


# {
#   責務: [
#     load_part: 指定IDのPartをPart Bankから取得する
#   ]
#   処理: [
#     1: IDを検証する
#     2: RepositoryからPartを読み込む
#     3: 未登録の場合は呼び出し元に分かるエラーを返す
#   ]
#   引数: [
#     part_id: 取得するPartのID
#     repository: Partを検索するRepository
#   ]
#   戻り値: [
#     part: 指定IDのPart
#   ]
#   エラー: [
#     ValueError: IDが不正、またはPartが未登録
#   ]
# }
def load_part(part_id: str, repository: PartRepository) -> Part:
    ...
```

このブロックは厳密なJSONとして解析するものではありません。`{}`、`項目名:`、複数行の`[]`を保ち、クラスでは「責務」「フィールド」を、関数・メソッドでは「責務」「処理」「引数」「戻り値」を書いてください。名前や処理内容をコードと一致させてください。

コード例はコメント形式を示すための抜粋です。型やimportを含む実装例ではありません。

## 4. 処理コメント

- 各意味のある処理単位の直前に通常コメントを置き、その処理の目的、理由、保つ不変条件を書いてください。
- JSON-like宣言コメントの「処理」は全体の手順を説明し、処理単位ごとの通常コメントは実装上の意図を補ってください。
- コードを日本語へそのまま置き換えただけのコメントを書かないでください。コメントが不要なほど自明な一行処理は、直前の処理単位のコメントに含めてください。
- コメントとコードの内容が変わったら、同じ変更でコメントを更新してください。

```python
# 入力ファイルが既に登録済みなら、再取り込みでPart IDを増殖させない。
if repository.has_source(checksum):
    return repository.get_source(checksum)

# 新規画像だけを展開し、抽出結果と元画像の登録を同じ処理単位で行う。
parts = extractor.extract(source_image)
repository.save_source_and_parts(source_image, parts)
```

## 5. 分割とファイル長

- 一つのモジュールには、同じ理由で変更される機能をまとめてください。
- 目安として300行を超えたファイルは分割できる責務を検討し、500行を超える場合は分割しない理由を明らかにしてください。
- 目安として50行を超えた関数・メソッドは、処理単位を抽出できるか検討してください。100行を超える場合は、処理を一つに保つ理由を示してください。
- 関数やクラスの行数にかかわらず、責務が複数なら分割してください。
- 小さすぎるファイルや意味のないラッパーを作り、定義を追う手間を増やさないでください。

## 6. 正しさ、安全性、性能

- 外部入力を境界で検証し、内部では確立した不変条件を使ってください。
- 例外を握りつぶさず、利用者が回復または原因特定できる情報を返してください。秘密情報や画像データなどを不用意にログへ出さないでください。
- ファイル操作は対象範囲を限定し、削除・上書き・パス解決の境界を明示してください。任意コマンド実行や`eval`などの動的実行を追加しないでください。
- SQLはパラメーター化し、トランザクション境界とロールバックを明示してください。
- 大量画像や大規模Part Bankを想定し、時間計算量・メモリ計算量を考慮してください。反復内の不要なディスクI/O、再計算、デコード、モデルロード、全件走査を避けてください。
- 最適化は正しさと読みやすさを保って行い、根拠が必要な場合は対象規模、計測方法、結果を記録してください。
- 依存関係を追加するときは、`pyproject.toml`へ必要な範囲とバージョン制約を宣言してください。開発環境だけで動き、通常のインストールやwheelで欠ける依存を作らないでください。

## 7. テストとCI

- 変更した処理について、正常系、失敗系、境界値を確かめるテストを追加してください。
- workflowを変更した場合はRuntimeまで、GUI操作を変更した場合はGUI経路まで、Part Bankを変更した場合は実ファイルとDBの永続化まで確認してください。
- E2Eではモックの成功と実データ・実モデルの成功を区別してください。未実行の層や前提条件を成功として報告しないでください。
- 一般的な開発手順とCIを通し、失敗を無視する設定やテスト削除で成功扱いにしないでください。
- テスト、wheel、実行時smokeのどこまで確認したかを、結果とともに報告してください。

## 8. 日本語ドキュメント

- 操作を説明するときは利用者を主語にし、「設定してください」「実行してください」のように書いてください。
- 機能やシステムの振る舞いを説明するときはアプリを主語にし、「検証します」「保存します」「エラーになります」のように書いてください。
- 新機能や運用手順を説明する場合は、背景、目的、手段、利用者の実行方法を記載してください。前提、入力、出力、エラー、制限も利用判断に必要な範囲で記載してください。
- 一文には主な内容を一つだけ置き、主語・対象・条件・結果の対応を明確にしてください。
- 曖昧な指示語、直訳調、名詞の連結、用語の揺れ、実装されていない機能を現在形で説明する書き方を避けてください。
- コマンドと設定例はそのまま実行できる形にし、実行ディレクトリや必要な依存関係を併記してください。
